# Основа аналитики воронки

## Выкатка

1. Применить миграцию `081_funnel_foundation.sql` обычным механизмом миграций
   **до** запуска новой версии backend. Миграция аддитивная; цены не меняет.
2. Выпустить backend, затем frontend. Новое поле `funnel` админского API добавлено
   без удаления legacy-полей. Старый frontend продолжает работать.
3. По проверенному списку оператора пометить тестовые аккаунты через защищённый
   admin API. Автоматически угадывать такие аккаунты нельзя.
4. Начиная с MR аналитики экспериментов, в обоих Compose-файлах
   `FUNNEL_EVENTS_ENABLE` по умолчанию равен `1`. Для аварийной остановки записи
   явно задать `FUNNEL_EVENTS_ENABLE=0` и пересоздать контейнер штатным способом.
5. Пройти подключение тестовым аккаунтом и проверить появление событий;
   убедиться, что коммерческие KPI не включают этот аккаунт.

Назначения экспериментов и canonical server facts не зависят от этого флага;
он управляет только best-effort interaction-событиями.

## Внутренние аккаунты

`POST /api/v1/admin/users/{internal_user_id}/internal`

Требуются admin-cookie и `x-csrf-token` текущей сессии. JSON:

```json
{"is_internal": true, "reason": "Личный тестовый аккаунт оператора"}
```

`is_internal` — строго boolean; причина — 1–300 символов после удаления пробелов.
Изменение и запись в `analytics_internal_audit` атомарны. Повтор с тем же значением
не создаёт дубль аудита. Для отмены отправить `false` с причиной.
Карточка и список пользователей возвращают флаг; пользователи из списка не скрыты.
Отдельного переключателя в интерфейсе в этом MR нет.

Флаг исключает аккаунт из выручки, платящих, регистраций, триалов, активных
подписок и конверсий ретроспективно. Не меняет доступ, платежи, рефералов или
уведомления. Трафик остаётся операционной метрикой **всех** пользователей.
При объединении web/Telegram внутренний статус распространяется на обе личности
и фиксируется в аудите. Снятие статуса с ранее объединённых аккаунтов требует
проверить обе записи.

## Определения

- `funnel_events` — SQL-представление существующих серверных фактов и новых
  взаимодействий. Регистрация берётся из identity, триал из сохранённого
  `trial_started_at`, оплата из ledger. Дополнительных записей в платёжной
  транзакции нет.
- `payment_succeeded` — accepted `subscription_activated`, положительная известная
  сумма в RUB, провайдер `yookassa`, `yookassa_v1`, `cryptobot` или `cryptobot_v1`.
  Гранты `grant:*`, доплаты за устройства, нулевые/неизвестные суммы и бонусный
  баланс не считаются внешней оплатой. При нестандартном PROVIDER_KEY требуется
  отдельно расширить определение — не включать все провайдеры без проверки.
- Когорта — триалы, начатые в выбранном периоде. Зрелость — прошло 10×24 часа.
  Конверсия — первая известная внешняя оплата пользователя в интервале
  `[trial_started_at, trial_started_at + 10 days)`. Предыдущие оплаты и продления
  не считаются первой оплатой внутри триала. При пустом зрелом знаменателе — null,
  а не 0%. Поэтому для периода 7 дней зрелой когорты ещё нет; используйте 30 дней.
- Legacy `kpi.trial_to_paid_rate` сохранён, но новая карточка использует только
  `funnel.trial_to_first_payment_rate` с числителем, знаменателем и ожидающими.

## События взаимодействия

При включённом флаге бот пишет `setup_started`, `platform_selected`,
`connection_confirmed`, `connection_problem`, `checkout_opened`; бот и web —
`payment_created` после успешного создания счёта подписки. Доплаты за устройства
не входят в эти события. Идемпотентность — по поверхности, имени события и ID
callback/счёта с префиксом провайдера. Никаких текстов сообщений, VLESS-ключей,
URL подписок, IP или произвольных payload в таблице нет.

`connection_confirmed` — **ответ пользователя**, не доказательство успешного
сетевого подключения. Создание счёта — не оплата. Полной телеметрии подключения
и frontend-кликов пока нет; это последующие этапы.

Ограничение записи — 200 мс, ошибки не распространяются в пользовательский
сценарий. Возможны потери событий при сбоях; это best-effort аналитика, не аудит
биллинга. Предыдущие клики не восстанавливаются. Историческая регистрация и
первый платёж ограничены полнотой существующих данных; старые NULL-суммы,
переносы/объединения аккаунтов могут искажать исторические когорты. Представление
не является неизменяемым журналом и не устраняет прежние особенности merge.

## Проверки и откат

На отдельной тестовой БД: `DATABASE_URL=<локальная тестовая БД> python -m pytest -q
tests/test_funnel_foundation.py tests/test_admin_stats.py tests/test_account_merge.py`.
Без БД: полный `python -m pytest -q`, `ruff check src tests`; frontend: `tsc --noEmit`.

Для остановки взаимодействий выключить флаг. Канонические факты и админская
статистика не зависят от флага. Для отката приложения вернуть предыдущую версию,
оставив аддитивные таблицы/столбец; down-migration и удаление данных не нужны.
