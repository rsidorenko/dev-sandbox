# Постоянные ключи bare Xray

После успешного перевыпуска/отзыва ключа backend сохраняет изменение в загрузочном `/usr/local/etc/xray/config.json` на каждом управляемом сервере **до** подтверждения API-операции. Перезапуск после завершённой операции не возвращает отозванный ключ; backend для самого старта Xray не нужен.

## Порядок и отказы

- Один host-lock: `config.json.bravada.lock` — отдельный файл, общий для всех inbound этого конфига.
- staged-файл проверяется `xray run -test`, сохраняет владельца/права. Затем fsync → atomic replace → fsync каталога → live RPC.
- Ошибка записи означает неуспех, live RPC не выполняется. Ошибка RPC не возвращает старые ключи на диск; ротация остаётся pending и повторяется.
- Reconcile сохраняет полный набор действующих пользователей, включая исправление устаревших disk-only записей. Совпадение email/UUID в памяти не отменяет эту проверку.
- На недоступном сервере отзыв не гарантируется до успешного завершения; нельзя сообщать пользователю об успешном перевыпуске при pending.

## Развёртывание и проверка

Нужны Python 3.10+, `/usr/local/bin/xray`, `/usr/local/bin/grpcurl`, `timeout`, root или `sudo -n` у существующего SSH-пользователя. Runtime-helper доставляется по SSH; ключи и payload передаются stdin, содержимое конфигурации не выводится.

После deploy дождаться reconcile без `persist_failed`, затем сравнить БД, live и постоянные UUID/flow всех управляемых inbound в режиме только чтения. Управляемые теги определяет `vpn_servers`; прочие inbound/маршруты/Reality остаются без изменений. Не перезапускать рабочие VPN-серверы только ради проверки: тест реального restart выполняется в изоляции.

## Операторские изменения и откат

`canonicalize_routing`, `enable_bare_xray_stats`, `cascade_apply_banks`, `cascade_apply_supercell` и `configure_xray_auto_selection` используют общий atomic writer. Он заново читает текущие clients под lock и переносит их в новую сетевую конфигурацию. Live GetInboundUsers больше не считается источником постоянных ключей: после неудачного отзыва там ещё может быть старый UUID.

**Нельзя восстанавливать полный старый config.json простым cp**, в том числе из `.pre-stats.bak`: такой backup содержит отозванные ключи. Для отката сетевых настроек использовать `apply_remote_config` с содержимым backup — он сохраняет текущие clients. Миграции/cutover, меняющие inbound-топологию, требуют отдельного окна: исключить конкурентный provisioning и сверить ключи с БД до открытия трафика. Исторические одноразовые scripts не являются безопасным способом обновления работающего флота.

Откат backend через revert не должен откатывать постоянные ключи. До возврата старой версии остановить перевыпуск, иначе гарантия сохранения снова теряется. Действующие сетевые соединения этим исправлением принудительно не разрываются.

## Воспроизводимый интеграционный тест
На изолированном Linux-хосте с Xray, grpcurl и curl: `cd backend && PYTHONPATH=src python tests/integration/xray_durable_restart.py`. Скрипт создаёт только временные конфиги и loopback-порты, проверяет TCP/XHTTP до и после restart собственного дочернего Xray и удаляет свои процессы/файлы. Рабочий systemd-сервис не используется.

Неопределённый SSH-сбой удерживает fleet-lock ещё 110 секунд после обнаружения сбоя, пока истечёт удалённый timeout с принудительным завершением. Это осознанная задержка: освобождение lock раньше могло бы позволить старой команде пережить новую ротацию.
