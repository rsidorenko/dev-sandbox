# Воронка бонусной кнопки рассылки

- Дата: 2026-09-25
- Статус: approved — пользователь поручил реализовать предложенное измерение пути до оплаты.
- План: `docs/superpowers/plans/2026-09-25-broadcast-bonus-funnel.md`

## Проблема и решение

После быстрого checkout (!195) job_id теряется в обычной кнопке do_pay, успешное
получение бонуса не фиксируется, а прямой путь обходит checkout_opened.
Нельзя достоверно связать рассылку и оплату по последнему промокоду пользователя.

Сохраняем явный job_id в компактной callback-кнопке только бонусного checkout.
При клике повторно проверяем получателя и TTL по broadcast_promo_claims, валидируем
план и число устройств. Обычный checkout не получает источник. Канонический расчёт
цены/скидки остаётся существующим; лучшая глобальная скидка не разрывает атрибуцию
перехода из рассылки. Callback ограничен 64 байтами.

Новая таблица событий: bonus_claimed, plan_selected, payment_created; стабильные
ключи дедупликации. Запись fail-open, ошибка аналитики не ломает покупку. Для созданного
платежа сохраняется payment_id YooKassa и internal_user_id. Успех отчёт определяет
по принятому ledger-событию этого платежа и пользователя; вебхук и fulfillment
не меняются. Не доверяем одному нажатию кнопки как факту оплаты.

В админке отдельная агрегированная таблица по последним 50 бонусным рассылкам:
уникальные получившие бонус/выбравшие тариф/создавшие/оплатившие; число платежей,
выручка. Покрытие — новые быстрые Telegram-кнопки, начиная с внедрения. Исторические
нулевые значения не интерпретируются как отсутствие продаж. Альтернативные способы
из общего меню отдельно не приписываются рассылке без подтверждённого источника.

## Влияние и приёмка

Миграция106 аддитивная. Биллинг, webhook, провайдеры VPN и отправка рассылок не меняются.
Тесты: чужой пользователь/TTL/битый callback, повтор клика/платежа, сбой аналитики,
глобальная скидка, обычная покупка без источника, только принятый ledger даёт успех.
Полный backend, реальная PostgreSQL, frontend typecheck, review/CI/merge/VPN smoke.
