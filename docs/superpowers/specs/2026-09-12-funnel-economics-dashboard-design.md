# Design Spec — Экономика рекламной воронки

- **Автор / ответственный:** команда Bravada VPN
- **Дата:** 2026-09-12
- **Статус:** approved — пользователь поручил реализацию
- **Связанный plan:** `docs/superpowers/plans/2026-09-12-funnel-economics-dashboard.md`

## Контекст и проблема

Текущая админская статистика показывает first-touch воронку `ads_*` / `tgads_*` до первой и второй
оплаты, но не хранит рекламный расход. Поэтому дешёвые регистрации и триалы невозможно сопоставить с
CAC, выручкой и ROAS. Автоматического импорта расходов Telegram Ads в проекте нет, а фактические
затраты оператор может получить из рекламного кабинета.

Нужен безопасный экономический слой поверх уже собранных атрибуций и внешних платёжных фактов. Он не
должен менять цены, создавать платежи или вмешиваться в VPN lifecycle.

## Цели

- Дать администратору ручной ввод расхода в рублях по campaign key и календарному дню.
- Показывать кампании с расходом, даже если они не дали ни одного атрибутированного пользователя.
- Считать по кампании расход, стоимость атрибутированного пользователя, стоимость триала, CAC,
  атрибутированную выручку и ROAS.
- Показывать суммарную рекламную экономику за выбранный период.
- Сохранить текущую зрелую 10-дневную конверсию отдельно от оперативного числа уже полученных клиентов.
- Исключать internal-аккаунты, операторские гранты и возвраты существующих плательщиков из acquisition.

## Non-goals

- Не подключать Telegram Ads API и не импортировать клики, показы, CPC или CTR.
- Не менять тарифы, скидки, промокоды, биллинг, выдачу ключей или lifecycle подписки.
- Не считать полный финансовый P&L: серверы, комиссии, налоги и поддержку.
- Не поддерживать валюты, отличные от RUB; оператор вводит уже приведённую рублёвую сумму.
- Не реализовывать multi-touch/last-touch и исторический backfill атрибуций.

## Текущее состояние

- `backend/migrations/081_funnel_foundation.sql` создаёт read-only view `funnel_events` из серверных
  фактов регистрации, триала и внешней оплаты.
- `backend/migrations/082_telegram_ads_attribution.sql` хранит неизменяемую first-touch атрибуцию с
  нормализованным campaign key.
- `backend/src/app/web_api/admin_stats.py` (`_telegram_ads_campaigns`) строит этапы кампаний и зрелую
  конверсию, но не имеет расхода или денежной атрибуции.
- `frontend/src/app/admin/stats/page.tsx` отображает кампании в общей вкладке статистики.
- `billing_events_ledger` является источником фактов выручки; внутренние гранты уже исключаются из
  глобальных KPI.

## Предлагаемое решение

### Хранение расхода

Аддитивная таблица `telegram_ads_spend_daily` хранит одну рублёвую сумму в копейках на
`(campaign_key, spend_date)`. Campaign key использует ту же грамматику, что и first-touch. Сумма `0`
удаляет строку, что позволяет исправить ошибочный ввод без отдельного интерфейса удаления.

Каждое фактическое изменение записывается в `telegram_ads_spend_actions` с actor и old/new суммой.
Повтор того же PUT не меняет строку и не создаёт новый audit event. Мутация защищена admin auth + CSRF
и выполняется одной транзакцией.

API принимает campaign key как `apk_01`, `ads_apk_01` или `tgads_apk_01`, но сохраняет единый
нормализованный ключ `apk_01`. Рубли передаются десятичной строкой и переводятся в копейки через
`Decimal`, без float-арифметики.

### Определения экономики

Когорта пользователей остаётся first-touch когортой: атрибуция произошла в выбранном периоде.
Расход берётся по локальным календарным датам того же периода.

- **Атрибутированный пользователь:** текущая метрика first-touch, не рекламный клик.
- **Полученный клиент:** глобально первая внешняя успешная оплата пользователя произошла после
  атрибуции и в пределах 10 дней после его триала. Зрелость когорты для этого оперативного счётчика не
  требуется: уже совершённая оплата является фактом.
- **CAC:** расход / полученные клиенты.
- **Стоимость пользователя:** расход / атрибутированные пользователи.
- **Стоимость триала:** расход / активированные после touch триалы.
- **Атрибутированная выручка:** сумма внешних accepted RUB-платежей полученных клиентов от их первой
  оплаты до момента отчёта. Продления входят; пользователи, платившие до рекламного touch, исключены.
- **ROAS:** атрибутированная выручка / расход. Это коэффициент `x`, не процент и не чистая прибыль.

Деление на ноль возвращает `null`, а UI показывает `—`. Кампания из таблицы расхода включается в
отчёт даже при нулевой воронке, чтобы расход без результата был виден.

## Альтернативы

- **Одна сумма на кампанию без даты.** Нельзя корректно переключать периоды и сравнивать окна.
- **Автоимпорт Telegram Ads.** Добавляет внешнюю интеграцию, валюты и секреты; слишком широк для этапа.
- **Зачесть всю выручку любого атрибутированного пользователя.** Возвращающиеся плательщики ошибочно
  приписали бы рекламе старую органическую ценность.
- **Считать CAC только по зрелым триалам.** Молодая кампания показывала бы ноль клиентов даже при уже
  совершённых оплатах; зрелая конверсия остаётся отдельной статистической метрикой.

## Влияние

- **Файлы:** новая миграция/репозиторий/admin endpoint, расширение admin stats и frontend-таблицы.
- **Миграции БД:** одна forward-only аддитивная миграция с двумя новыми таблицами и индексом по дате;
  существующие данные не изменяются.
- **Безопасность:** mutation только под admin JWT + CSRF; campaign allowlist; лимит суммы; audit trail.
- **Биллинг:** ledger только читается; таблицы, цены, apply/fulfillment и промокоды не изменяются.
- **Retention / VPN:** не затрагиваются; запросы не вызывают provider и не меняют snapshots.

## Открытые вопросы

- Автоматический импорт показов/кликов и расхода можно добавить отдельной интеграцией после проверки
  полезности ручной модели.
- При появлении существенной валютной рекламы понадобится отдельный курс и валюта источника, а не
  неявное смешивание с RUB.

## Критерии приёмки

- [ ] Миграция повторяемая, аддитивная и не затрагивает billing/VPN таблицы.
- [ ] PUT расхода валидирует CSRF, campaign/date/amount и идемпотентен по состоянию и audit trail.
- [ ] `ads_*`, `tgads_*` и чистый key сходятся в одну запись.
- [ ] Кампания с расходом и нулём пользователей видна в отчёте.
- [ ] CAC/CPL/CPT/выручка/ROAS корректны, нулевые знаменатели дают `null`.
- [ ] Existing payer и internal-аккаунт не создают рекламную выручку.
- [ ] UI позволяет сохранить/обнулить дневной расход и показывает итог/экономику по кампании.
- [ ] Полные backend/frontend тесты, lint, build и release checks зелёные.
