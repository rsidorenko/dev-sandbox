# Design Spec — Собственная аналитика и эксперименты

- **Автор / ответственный:** Codex
- **Дата:** 2026-09-17
- **Статус:** approved
- **Связанный plan:** `docs/superpowers/plans/2026-09-17-analytics-experiments.md`

## Контекст и проблема

В продукте уже есть серверные факты регистрации, триала и оплаты, а также часть событий
Telegram/web checkout. Админка показывает KPI и рекламу Telegram, но не даёт общей
продуктовой воронки. Изменения интерфейса выкатываются всем пользователям сразу: нет
стабильного назначения варианта, факта экспозиции и отчёта по оплатам/выручке варианта.

Внешняя Метрика намеренно выключена без consent, поэтому критические решения должны
опираться на собственные минимальные server-side данные без cookies третьих сторон и PII.

## Цели

- Показать в админке first-party воронку всех неслужебных пользователей за период.
- Добавить стабильные, сохраняемые в PostgreSQL назначения A/B-вариантов.
- Запустить первый безопасный эксперимент `checkout_reassurance_v1` на checkout.
- Показывать по вариантам экспозиции, созданные платежи, успешные оплаты, выручку и конверсию.
- Не позволять аналитике или экспериментам ломать checkout и оплату.

## Non-goals

- Не строить универсальный визуальный редактор экспериментов.
- Не принимать произвольные анонимные события из интернета.
- Не отправлять PII, URL платёжного провайдера, токены или содержимое форм.
- Не объявлять победителя автоматически при малой выборке.

## Текущее состояние

- `backend/src/app/application/funnel_events.py` валидирует ограниченный набор событий и
  пишет их best-effort в `funnel_interactions`.
- `backend/migrations/081_funnel_foundation.sql` создаёт canonical view `funnel_events`.
- `backend/src/app/web_api/admin_stats.py` показывает общие KPI, зрелую trial→paid
  конверсию и отдельную воронку Telegram Ads.
- `frontend/src/shared/lib/analytics.ts` работает только с опциональной Яндекс.Метрикой.
- `frontend/src/app/(site)/(protected)/payment/[planId]/page.tsx` не имеет назначения
  эксперимента и выкатывает один UI всем пользователям.

## Предлагаемое решение

Создать append-only таблицу `experiment_assignments` с ключом
`(internal_user_id, experiment_key)`, вариантом и временем первой экспозиции. Активные
эксперименты описываются строгим allowlist в домене. Вариант выбирается детерминированно
SHA-256-хешем `experiment_key + internal_user_id`, а результат сохраняется; повторные
запросы и смена процесса не меняют вариант.

Защищённый endpoint resolve принимает только allowlisted experiment key. Он идемпотентно
создаёт/возвращает назначение. Ошибка endpoint на фронте означает control, поэтому checkout
остаётся доступен. Первый эксперимент меняет только reassurance-copy под кнопкой оплаты:
`control` против `reassurance`; цена, доступность методов и платёжный код идентичны.

Отчёт админки агрегирует назначения по варианту, а затем связывает их по internal_user_id
с `payment_created` и canonical accepted payment facts, произошедшими после экспозиции.
Отдельный product funnel считает distinct пользователей по серверным событиям за выбранный
период. Служебные аккаунты исключаются.

## Альтернативы

- Только Яндекс.Метрика: требует consent и оставляет ключевые данные у третьей стороны.
- Клиентское случайное назначение: теряется при очистке storage и допускает переключение.
- Feature flags без отчёта: позволяют rollout, но не отвечают, повлияло ли изменение на оплату.
- Публичный endpoint анонимных событий: расширяет поверхность злоупотреблений и не нужен
  для первого эксперимента на авторизованном checkout.

## Влияние

- **Файлы:** новый experiment domain/API, web app routes, admin stats, checkout и типы UI.
- **Миграции БД:** одна новая append-only таблица и индексы; destructive DDL нет.
- **Безопасность:** endpoint только под JWT, ключи/варианты из allowlist, PII в payload нет.
- **Биллинг:** результат эксперимента читает ledger, но не меняет UC-04/UC-05 и суммы.
- **Retention / lifecycle:** не затрагивается.
- **VPN-провайдер:** не затрагивается.

## Критерии приёмки

- [x] Один пользователь всегда получает один и тот же вариант эксперимента.
- [x] Неизвестный experiment key отклоняется, сбой resolve не блокирует checkout.
- [x] Checkout реально отображает control/reassurance без изменения платёжной логики.
- [x] Админка показывает общую продуктовую воронку и результаты вариантов.
- [x] Оплаты и выручка считаются только после экспозиции и исключают служебные аккаунты/гранты.
- [x] Тесты покрывают детерминизм, API, SQL-агрегацию и UI-варианты.
- [x] Полные backend/frontend тесты, build, E2E и release readiness зелёные.
