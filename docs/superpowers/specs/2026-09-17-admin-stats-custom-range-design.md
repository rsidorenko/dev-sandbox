# Design Spec — Очистка и произвольный период статистики

- **Автор / ответственный:** команда Bravada VPN
- **Дата:** 2026-09-17
- **Статус:** approved
- **Связанный plan:** `docs/superpowers/plans/2026-09-17-admin-stats-custom-range.md`

## Контекст и проблема

Админская статистика считает пользователей с first-touch атрибуцией `nakrut`, хотя этот
источник содержит накрученные регистрации и не должен влиять на продуктовые или финансовые
агрегаты. Данные удалять нельзя: атрибуция нужна для аудита и диагностики источника.

Экран `frontend/src/app/admin/stats/page.tsx` поддерживает только фиксированные периоды
`1d/7d/30d/90d/all`. Оператору нужен произвольный диапазон дат для сравнения рекламных запусков
и зрелых когорт.

## Цели

- Исключить пользователей с `telegram_ads_attributions.campaign_key = 'nakrut'` из всех
  агрегатов `/api/v1/admin/stats`, как сейчас исключаются служебные аккаунты.
- Не удалять пользователей, атрибуцию, платежи или VPN-данные.
- Добавить выбор начальной и конечной даты в админке с сохранением быстрых периодов.
- Считать обе выбранные даты включительно в выбранной часовой зоне.
- Ограничить произвольное окно 366 днями для защиты тяжёлого агрегирующего эндпоинта.

## Non-goals

- Не скрывать `nakrut` из управления пользователями и не удалять эти аккаунты.
- Не добавлять UI управления списком исключённых кампаний.
- Не менять оплату, выдачу VPN, lifecycle подписок и сбор исходных событий.
- Не перерабатывать семантику текущего gauge «Активных подписок сейчас».

## Текущее состояние

- `backend/src/app/web_api/admin_stats.py:65` вычисляет только нижнюю границу фиксированного
  периода; большинство SQL-запросов не имеют верхней границы.
- `backend/src/app/web_api/admin_stats.py:649` валидирует только фиксированные ключи периода.
- `frontend/src/features/admin/api.ts:108` передаёт в API только `period` и `tz`.
- `frontend/src/app/admin/stats/page.tsx:30` показывает только пять быстрых периодов.
- `backend/migrations/082_telegram_ads_attribution.sql` хранит неизменяемую first-touch
  атрибуцию пользователя и позволяет надёжно определить `nakrut`.

## Предлагаемое решение

Добавить read-only представление `analytics_eligible_user_ids`, включающее только внешних
пользователей без атрибуции `nakrut`. Все пользовательские агрегаты статистики используют это
представление как единый источник eligibility. Рекламная таблица также исключает саму кампанию
`nakrut` и её расход.

API принимает `period=custom&date_from=YYYY-MM-DD&date_to=YYYY-MM-DD`. Даты интерпретируются
как локальные календарные дни в разрешённой IANA-зоне; временной интервал внутри SQL остаётся
полуоткрытым `[from_ts, to_ts)`. Для текущего дня верхняя граница ограничивается текущим
моментом. API возвращает локальные `date_from` и `date_to` вместе с UTC-границами.

Фронтенд показывает кнопку «Свой период», два date-input и кнопку применения. Изменение полей
само по себе не запускает запрос. Быстрые периоды продолжают работать без изменения URL-контракта.

## Альтернативы

- Удалить `nakrut`-аккаунты: отвергнуто как разрушительное и лишающее аудита.
- Расставить `campaign_key <> 'nakrut'` во всех SQL: отвергнуто из-за риска пропустить агрегат.
- Добавить флаг в `user_identities`: отвергнуто, потому что потребовалась бы синхронизация флага
  при появлении атрибуции.

## Влияние

- **Файлы:** миграция eligibility-view, `admin_stats.py`, интеграционные тесты, типы/API/UI
  админки, frontend unit-тест.
- **Миграции БД:** additive `CREATE OR REPLACE VIEW`, без изменения или удаления данных.
- **Безопасность:** параметры дат валидируются и не интерполируются в SQL.
- **Биллинг:** ledger не изменяется; фильтр применяется только при чтении статистики.
- **Retention / lifecycle:** без влияния.
- **VPN-провайдер:** без влияния; трафик только агрегируется для eligible-пользователей.

## Критерии приёмки

- [x] `nakrut` отсутствует в рекламных кампаниях и не влияет на KPI, серии, воронки,
      эксперименты, активные подписки, выручку и трафик.
- [x] Данные `nakrut` остаются в исходных таблицах.
- [x] Произвольный диапазон включает обе выбранные календарные даты.
- [x] Неполные, перевёрнутые, будущие и превышающие 366 дней диапазоны дают HTTP 400.
- [x] Быстрые периоды сохраняют прежнее поведение.
- [x] Тесты backend и frontend покрывают фильтр и пользовательский диапазон.
- [x] Полный pytest, frontend test/build и release health проходят.
