# Design Spec — сохранение контекста при повторном подключении

- **Автор:** rsidorenko
- **Дата:** 2026-09-12
- **Статус:** approved
- **Связанный plan:** `docs/superpowers/plans/2026-09-12-connect-retry-context.md`
- **Ветка:** `fix/connect-retry-context`

## Контекст и проблема

Одноэкранный fast path рекомендует Happ на iOS, Android и macOS и Karing на Windows. Сейчас
кнопка «Не получилось» переиспользует callback старой Karing-инструкции. Поэтому «Начать
заново» после fast path переводит пользователя с Happ на первый шаг Karing без объяснения, а
«Назад» уже ведёт в выбор приложения. Это увеличивает путаницу в самом чувствительном месте
воронки `trial → первое подключение`.

## Цели

- Разделить проблему fast path и проблему существующей пошаговой инструкции.
- Повтор fast path возвращает на тот же экран, с тем же устройством и рекомендуемым приложением.
- На iOS, Android и macOS дать явный переход к выбору другого приложения.
- Сохранить Karing основным и единственным приложением fast path для Windows.
- Не изменить работающие callbacks старых сообщений и поведение пошаговой Karing-инструкции.

## Non-goals

- Не менять тарифы, триал, оплату, выдачу VPN-конфигурации или формат подписки.
- Не добавлять новые приложения и deep-link схемы.
- Не менять отдельный сценарий Smart TV.
- Не добавлять новый экран проверки результата в подробную Happ-инструкцию: сейчас она
  завершается подтверждением успеха и не содержит кнопки «Начать заново».

## Текущее состояние

- `backend/src/app/bot_transport/storefront_ui.py:1958` (`_FAST_PROBLEM_CALLBACK`) направляет
  fast path в общие `*_NO` callbacks.
- `backend/src/app/bot_transport/storefront_ui.py:1004`, `1142`, `1500`, `1916` формируют
  общие экраны проблемы с `*_RETRY` callbacks.
- `backend/src/app/bot_transport/runtime_facade.py:407` (`_step_1_for_retry`) направляет эти
  callbacks на первый шаг Karing для iOS, Android, macOS и Windows.
- `backend/src/app/bot_transport/runtime_facade.py:2757` не различает источник экрана проблемы.
- `backend/tests/test_trial_connect_fastpath.py:128` проверяет содержимое fast path, но не
  маршрут `fast path → проблема → повтор`.

## Предлагаемое решение

1. Добавить отдельный префикс callback для проблемы fast path с платформой в payload. Парсер
   принимает только четыре разрешённые платформы и не переносит URL или другие данные.
2. На экране проблемы fast path показывать:
   - «Повторить подключение» — возвращает в `connect_fast_<platform>`;
   - «Выбрать другое приложение» — открывает существующий chooser для iOS/Android/macOS;
   - для Windows вместо выбора приложения — существующую подробную инструкцию Karing;
   - поддержку и возврат к выбору устройства.
3. Общие `*_NO`/`*_RETRY` callbacks подробной Karing-инструкции оставить без переименования:
   «Начать заново» по-прежнему открывает Karing step 1 выбранной платформы.
4. Событие нового fast-problem callback учитывать как `connection_problem`, чтобы изменение
   навигации не создало разрыв в аналитике воронки.

## Альтернативы

- Хранить выбранное приложение в памяти процесса — отклонено: состояние потеряется при
  рестарте и усложнит горизонтальный запуск.
- Переиспользовать `*_NO` и определять источник по предыдущему сообщению — отклонено: Telegram
  callback не несёт надёжного контекста предыдущего экрана.
- Всегда возвращать в chooser — отклонено: это добавляет лишний шаг пользователю, который хочет
  просто повторить короткий сценарий.

## Влияние

- **Файлы:** `backend/src/app/bot_transport/storefront_ui.py`,
  `backend/src/app/bot_transport/runtime_facade.py`,
  `backend/src/app/application/funnel_events.py`, тесты fast path/funnel.
- **Миграции БД:** нет.
- **Безопасность:** callback содержит только allowlist-платформу; subscription URL остаётся на
  серверном рендере и не попадает в callback.
- **Биллинг:** не затрагивается.
- **Retention / lifecycle:** не затрагивается.
- **VPN-провайдер:** только повторное чтение существующего конфига при возврате в fast path;
  CRUD, Reality TLS и `limitIp` не меняются.

## Открытые вопросы

- Если для Windows появится второй поддерживаемый клиент, отдельный chooser можно добавить
  позднее без изменения нового callback-контракта.

## Критерии приёмки

- [x] Для iOS/Android/macOS маршрут `fast path → проблема → повтор` возвращает тот же Happ fast path.
- [x] Для Windows тот же маршрут возвращает Karing fast path.
- [x] «Выбрать другое приложение» открывает chooser на iOS/Android/macOS.
- [x] Windows предлагает подробную Karing-инструкцию и не показывает ложный выбор приложения.
- [x] Пошаговый Karing retry возвращает на Karing step 1 своей платформы.
- [x] Новый callback фиксируется как `connection_problem` с корректной платформой.
- [x] Старые callbacks продолжают обрабатываться.
- [x] `pytest -q`, Ruff и `python scripts/run_mvp_repo_release_health_check.py` проходят.
