# Design Spec — зрелое окно notification holdout

- **Автор / ответственный:** rsidorenko
- **Дата:** 2026-09-20
- **Статус:** approved
- **Связанный plan:** `docs/superpowers/plans/2026-09-20-notification-holdout-window.md`

## Контекст и проблема

Текущая holdout-статистика использует календарный `sent_date` вместо точного `sent_at`, фактически открывает окно до восьми календарных дат и может засчитать оплату до реальной отправки. Свежие уведомления сразу входят в знаменатель, хотя ещё не получили полные семь суток на конверсию.

## Цели

- Считать оплату строго в полуинтервале `[sent_at, sent_at + 7 days)`.
- Сравнивать delivered и holdout только на зрелых наблюдениях.
- Сохранять видимость общего числа и ожидающих наблюдений.

## Non-goals

- Не менять алгоритм назначения holdout и отправку уведомлений.
- Не менять billing ledger и обработку платежей.

## Предлагаемое решение

Для каждой пары пользователь/тип/status в выбранном периоде брать первое точное `sent_at`. Наблюдение считается зрелым, если к концу отчёта прошло семь суток. `paid_users` и `paid_rate` вычисляются только по зрелым наблюдениям и точному семисуточному окну. API дополнительно возвращает `total_users` и `pending_users`, UI показывает зрелые/всего.

## Влияние

- **Миграции:** не требуются.
- **Биллинг:** только read-only запрос к accepted external payments.
- **Уведомления:** scheduler и delivery не меняются.

## Критерии приёмки

- [ ] Оплата до `sent_at` не засчитывается.
- [ ] Оплата после семи суток не засчитывается.
- [ ] Незрелые уведомления видны, но не входят в CR.
- [ ] Delivered и holdout используют одинаковое окно.
- [ ] Backend/PG/frontend тесты зелёные.
