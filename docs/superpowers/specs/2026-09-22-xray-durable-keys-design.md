# Постоянное сохранение отзыва ключей Xray

Дата: 2026-09-22. Статус: reviewed. Пользователь разрешил реализацию и merge.

## Проблема и цель
Успешный отзыв/перевыпуск ключа через API сейчас меняет только память Xray. После рестарта загружается старый `config.json`. MR !179 исправляет это периодически, но оставляет окно повторного доступа. Цель: после подтверждённой ротации перезапуск не восстанавливает старый ключ, даже если backend недоступен.

## Решение
На каждом bare_xray-хосте изменения клиентов сначала записываются в настоящий загрузочный конфиг, затем применяются через API. Удалённая операция держит отдельный flock на весь цикл чтение → проверка → атомарная запись → RPC. Запись: временный файл в том же каталоге, сохранение владельца/прав, проверка Xray, fsync файла, replace, fsync каталога. Ошибка диска запрещает RPC и успешное подтверждение; ошибка API не откатывает отозванный ключ на диск. Отмена async-задачи дожидается всей операции. При неопределённом SSH-результате логическая блокировка удерживается до окончания remote timeout (100 с) + kill-after (5 с) + запаса, чтобы старая операция не пережила следующую ротацию.

Reconcile сохраняет полный желаемый набор управляемого inbound, включая исправление disk-only записей. Совпадающий конфиг не переписывается. Остальные inbound, маршруты, TLS/Reality и outbound не меняются.

Онлайн-скрипты маршрутизации и статистики получают общий host-lock и используют актуальных клиентов с диска вместо устаревающего live-снимка. Прямой откат старого полного конфига запрещён runbook: сетевые настройки откатываются с сохранением текущих clients. Миграции/cutover выполняются отдельно, при остановленных конкурентных операциях и сверке с БД перед открытием трафика.

## Подтверждённые условия
Read-only обследование семи хостов: Python 3.10, sudo/root доступны, загрузочный путь `/usr/local/etc/xray/config.json`, бинарник `/usr/local/bin/xray`, файл обычный. Постоянные списки действительно отстают от live (58/70 против 62).

## Альтернативы и границы
Загрузка БД непосредственно при каждом старте потребовала бы новых секретов/сетевой зависимости и недоступности VPN при отказе backend. Сохраняем актуальный локальный конфиг. Не меняем текущие ключи пользователей и не перезапускаем production Xray для проверки. Проверка реального рестарта — на изолированном экземпляре. Не обещаем отзыв на недоступном сервере до успешного завершения операции; pending-ротация сохраняется и повторяется.

## Влияние
Новый stdlib-модуль удалённой транзакции, XrayApiClient, reconcile, пять онлайн-операторских скриптов, тесты и runbook. Миграций БД нет. Billing/retention и 3x-ui CRUD не меняются. Секреты передаются SSH stdin и не попадают в stdout/argv диагностики.

## Приёмка
- Старый UUID отсутствует после изолированного рестарта без reconcile, новый принимается.
- Сбой сохранения не меняет live-состояние и не завершает ротацию.
- RPC-сбой/отмена не возвращают старый ключ на диск; повтор безопасен.
- TCP/XHTTP, disk-only старые записи, параллельные inbound одного хоста и повторные операции покрыты тестами.
- Полный pytest, PostgreSQL-ротация, ruff, health check, review и CI зелёные.
- После deploy дисковые UUID/flow соответствуют БД на всех 11 управляемых inbound, production healthy.

Источники: [официальный API](https://xtls.github.io/en/config/api.html), [реализация HandlerService](https://github.com/XTLS/Xray-core/blob/main/app/proxyman/command/command.go).

## Результаты проверки
Полный pytest: 2564 passed, 155 skipped; PostgreSQL-ротация: 16 passed. Реальный изолированный Xray 26.6.22: после restart старые TCP/XHTTP ключи отклоняются, новые работают, повтор add идемпотентен. Xray-проверка временных копий всех 11 production inbound прошла.
