# Design — безопасный сброс тестового пользователя

- **Дата:** 2026-09-13
- **Ветка:** `feat/admin-test-user-reset`
- **Статус:** approved for implementation

## Контекст

Telegram-пользователь может активировать пробный период только один раз. Разработчику,
который проверяет полный сценарий бота, сейчас приходится вручную чистить PostgreSQL и VPN-панели.
Простое удаление `user_identities` некорректно: `internal_user_id` детерминирован как `u<telegram_id>`,
поэтому при следующем `/start` старые записи снова относятся к тому же пользователю.

## Цель

Добавить в админку управляемый сброс аккаунта, после которого следующий `/start` проходит как
для нового пользователя: регистрация отсутствует, триал снова доступен, подписки и ключей нет,
старые funnel/traffic данные не приклеиваются к новой сессии.

## Не цели

- Общее удаление реальных пользователей.
- GDPR/self-service удаление аккаунта.
- Изменение логики триала, оплаты или выдачи VPN.
- Автоматическое определение тестовых аккаунтов.

## Безопасный контракт

1. Сброс разрешён только при `user_identities.is_internal = TRUE`.
2. Оператор вводит точный Telegram ID пользователя и причину длиной 1–300 символов.
3. Endpoint защищён admin auth и CSRF.
4. До удаления БД вызывается существующий `vless_provider.delete_user` для всех VPN-серверов.
5. При `unavailable/error` БД не изменяется. `success/not_found` допускают продолжение.
6. После отзыва ключей все пользовательские строки удаляются одной PostgreSQL-транзакцией.
7. Независимый audit сброса остаётся после удаления identity и не имеет FK на неё.
8. Обычный пользователь получает отказ, даже если подтверждение введено верно.

## Очищаемое состояние

- identity, subscription snapshot, issuance state;
- billing ingestion/apply state для этого internal ID;
- собственные referral relationship/balance/transactions/bonus awards пользователя;
- email link/verification state and web notifications;
- promo intent/redemptions с корректировкой глобального redemption counter;
- notification/funnel/Telegram Ads attribution;
- broadcast claims по Telegram ID;
- bare_xray traffic state/daily для обоих email-контрактов;
- операторские subscription actions, относящиеся к удаляемому тестовому пользователю.

`analytics_internal_audit` сохраняется как исторический аудит маркировки. Новый аккаунт создаётся
с `is_internal = FALSE` и перед следующим сбросом должен снова быть явно помечен тестовым.
Начисления и связи, принадлежащие другим пользователям, сохраняются: сброс не списывает чужой
баланс и не переписывает сторонний финансовый аудит.

## API

### Маркировка

Используется существующий endpoint:

`POST /api/v1/admin/users/{internal_user_id}/internal`

Админка получает UI для включения/выключения флага с обязательной причиной.

### Сброс

`POST /api/v1/admin/users/{internal_user_id}/reset-test-account`

Body:

```json
{
  "confirmation_telegram_user_id": 123456789,
  "reason": "Повторная проверка trial flow"
}
```

Success возвращает Telegram/internal ID, VPN outcome, correlation ID и количество удалённых строк.

## UI

- В таблице появляется тип `Обычный` / `Тестовый`.
- Действие маркировки открывает отдельное подтверждение с причиной.
- `Сбросить` показывается только тестовым аккаунтам.
- Модальное окно перечисляет последствия и требует вручную ввести Telegram ID.
- После успеха пользователь исчезает из списка; оператор видит понятное подтверждение.

## Миграция

`084_admin_user_reset_actions.sql` создаёт append-only таблицу аудита. Миграция additive и
идемпотентна; существующие таблицы и данные не меняет.

## Инварианты и риски

- VPN delete выполняется до удаления identity, чтобы не оставить бесхозный активный ключ.
- Транзакционная очистка выполняется только после повторной блокировки и проверки identity.
- Повторный запрос после успешного сброса получает `user_not_found` и не создаёт второй audit.
- Во время сброса тестировщик не должен параллельно запускать оплату или `/start`; UI явно это укажет.
- История сбросов сохраняет только служебные ID, причину, actor и агрегированные counts — без секретов.

## Acceptance criteria

- Обычного пользователя сбросить нельзя.
- Неверный Telegram ID, отсутствующие auth/CSRF или причина отклоняются.
- Ошибка VPN-провайдера оставляет данные пользователя неизменными.
- Успешный сброс удаляет весь перечисленный state и VPN-конфигурацию.
- Следующее создание identity имеет `trial_used = FALSE` и не имеет subscription snapshot.
- Backend/frontend тесты и PostgreSQL migration smoke зелёные.
