# Design Spec — полная рекламная воронка в админке

- **Автор:** rsidorenko
- **Дата:** 2026-09-12
- **Статус:** approved
- **Связанный plan:** `docs/superpowers/plans/2026-09-12-full-funnel-metrics.md`
- **Ветка:** `feat/full-funnel-metrics`

## Контекст и проблема

Админка уже показывает экономику Telegram Ads и часть продуктовых событий, но названия двух
колонок переоценивают их смысл: `setup_started` означает открытие экрана подключения, а
`connection_confirmed` — ручное подтверждение пользователя. При этом собранные
`platform_selected` и `connection_problem` не видны, а работающий bare_xray-коллектор не
используется для оценки первого реального VPN-трафика рекламной когорты.

В результате оператор видит «2 настройки / 0 подключений», но не может отличить открытый экран,
фактический трафик, ручное подтверждение и проблему пользователя.

## Цели

- Показать в админке все собираемые этапы рекламной воронки и их точные определения.
- Построить последовательность `триал → открыли подключение → первый VPN-трафик → подтвердили
  работу → checkout → счёт создан → оплата`.
- Показать побочные сигналы: выбор платформы, распределение платформ, сообщение о проблеме,
  зрелость триалов и повторную оплату.
- Добавить первый VPN-трафик без изменения VPN-провайдера и без записи новых событий в
  критический путь.
- Сохранить first-touch, 10-дневное окно приобретения и текущую экономику CAC/ROAS.

## Non-goals

- Не превращать экран продуктовой статистики в мониторинг логов, серверов и исключений.
- Не добавлять клики/показы Telegram Ads: Telegram не передаёт их текущему backend.
- Не менять тарифы, триал, оплату, VPN CRUD или правила атрибуции.
- Не считать ручное подтверждение доказательством технического подключения.
- Не вводить новую миграцию только ради производного показателя трафика.

## Текущее состояние

- `backend/src/app/web_api/admin_stats.py:183` (`_TELEGRAM_ADS_CAMPAIGNS`) считает атрибуцию,
  триалы, `setup_started`, `connection_confirmed`, checkout, созданный счёт и оплаты.
- `backend/src/app/application/funnel_events.py:9` перечисляет собираемые взаимодействия:
  `setup_started`, `platform_selected`, `connection_confirmed`, `connection_problem`,
  `checkout_opened`, `payment_created`.
- `backend/migrations/081_funnel_foundation.sql:32` добавляет серверные факты регистрации,
  триала и успешной оплаты в read-only view `funnel_events`.
- `backend/migrations/079_bare_xray_traffic.sql:24` хранит дневной per-user трафик по email
  `user-<internal_id[:16]>`/`x-user-<internal_id[:16]>`.
- `frontend/src/app/admin/stats/page.tsx:427` показывает campaign-таблицу, но скрывает
  платформу, проблему и фактический трафик.

## Предлагаемое решение

1. Расширить campaign SQL производными флагами на пользователя после старта его триала:
   открытие подключения, выбор платформы, подтверждение, проблема, checkout и созданный счёт.
2. Считать `first_vpn_traffic_users` как пользователей когорты, для которых после календарного
   дня старта триала по MSK есть положительный `uplink + downlink` в
   `bare_xray_traffic_daily`. Использовать существующий контракт email и индекс `(email,
   stat_date)`. Это «первый наблюдаемый трафик» с дневной точностью, а не сетевой handshake.
3. Вернуть в API все этапы по каждой кампании и общий объект `telegram_ads.funnel`, рассчитанный
   по всем кампаниям до ограничения таблицы в 200 строк.
4. Добавить platform breakdown для iOS/Android/macOS/Windows/TV и количество пользователей,
   сообщивших о проблеме.
5. В UI:
   - переименовать «Настройка» в «Открыли подключение»;
   - переименовать «Подключились» в «Подтвердили работу»;
   - добавить «Первый VPN-трафик»;
   - показать общую последовательность этапов с step-to-step конверсией;
   - вывести все новые метрики в campaign-таблице и пояснить определения.

## Альтернативы

- Записывать новый `first_traffic` event из коллектора — отложено: потребует миграции и нового
  write-path; существующей дневной таблицы достаточно для текущего когортного отчёта.
- Считать `connection_confirmed` реальным подключением — отклонено: это только Telegram callback.
- Показывать только общую воронку без campaign breakdown — отклонено: нельзя принимать решения
  по рекламным источникам.

## Влияние

- **Файлы:** `backend/src/app/web_api/admin_stats.py`, backend-тесты экономики/атрибуции,
  `frontend/src/entities/admin/types.ts`, `frontend/src/app/admin/stats/page.tsx`.
- **Миграции БД:** нет; используется существующий индекс трафика.
- **Безопасность:** наружу выходят только агрегаты; internal id и traffic email не возвращаются.
- **Биллинг:** read-only расчёт существующих accepted payment facts; UC-04/UC-05 не меняются.
- **Retention / lifecycle:** не затрагивается.
- **VPN-провайдер:** не затрагивается; читается агрегированная таблица коллектора.

## Открытые вопросы

- Если понадобится точное время первого трафика, сделать отдельную фичу с идемпотентным
  first-observed event из коллектора и миграцией.

## Критерии приёмки

- [ ] API возвращает все этапы, проблему и platform breakdown по кампании и суммарно.
- [ ] Первый VPN-трафик считается только для рекламной когорты после старта триала.
- [ ] Общая цепочка показывает количество и конверсию между соседними этапами.
- [ ] Campaign-таблица использует точные названия и показывает новые метрики.
- [ ] Пустые выборки и нулевые знаменатели не дают `NaN`/деление на ноль.
- [ ] В API не возвращаются идентификаторы пользователей или traffic email.
- [ ] Полные backend/frontend проверки и release health-check проходят.
