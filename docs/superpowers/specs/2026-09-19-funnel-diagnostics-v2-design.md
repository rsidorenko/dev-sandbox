# Design Spec — Диагностика воронки v2

- **Автор / ответственный:** команда Bravada VPN
- **Дата:** 2026-09-19
- **Статус:** approved
- **Связанный plan:** `docs/superpowers/plans/2026-09-19-funnel-diagnostics-v2.md`

## Контекст и проблема

Текущая воронка различает открытие настройки, первый положительный VPN-трафик и ручное
подтверждение работы. Любой положительный байт, включая технический обмен клиента, сейчас
выглядит как использование продукта. Также невозможно увидеть возврат пользователя на D1/D2/D3
и понять, какой путь подключения он проходил: короткий direct или подробный guided.

Без этих различий нельзя отделить проблему установки от проблемы качества VPN после подключения.

## Цели

- Добавить понятие meaningful traffic: не менее 1 МиБ VPN-трафика пользователя после старта
  триала в пределах аналитического окна.
- Считать D1/D2/D3 retention только по полностью завершённым локальным дням и только при
  meaningful traffic в соответствующий день.
- Инструментировать входы в direct и guided маршруты подключения без изменения маршрутизации.
- Вывести агрегаты в `/api/v1/admin/stats` и базово показать их на текущем экране статистики.
- Добавить meaningful traffic в рекламную воронку рядом с первым техническим трафиком.

## Non-goals

- Не менять продолжительность триала, тарифы, оплату или правила выдачи VPN-доступа.
- Не выполнять автоматическую проверку соединения — это отдельная фича
  `feat/vpn-connection-check`.
- Не строить разрезы качества по серверам и когортную матрицу — это задача
  `feat/admin-quality-dashboard`.
- Не считать 1 МиБ универсальной бизнес-константой навсегда: порог возвращается в API явно.

## Текущее состояние

- `backend/src/app/application/funnel_events.py` принимает ограниченный набор interaction-событий,
  но не хранит маршрут подключения.
- `backend/src/app/bot_transport/runtime_facade.py` отображает fast path через `connect_fast_*` и
  подробные инструкции через `connect_*`, используя общий безопасный recorder.
- `backend/src/app/persistence/postgres_traffic_stats.py` атомарно накапливает суточные байты в
  `bare_xray_traffic_daily` и запускает clock триала при первом положительном приросте.
- `backend/src/app/web_api/admin_stats.py` считает `first_vpn_traffic_users` по условию `bytes > 0`,
  но не отличает значимое использование и возвраты.

## Предлагаемое решение

Миграция добавляет в `funnel_interactions` поле `connection_route` со значениями
`'' | direct | guided`. Recorder валидирует поле, а transport присваивает `direct` fast path и
`guided` подробным платформенным инструкциям. Существующие события и callback-контракты
сохраняются.

Новый read-only агрегат `funnel_diagnostics_v2` строится из eligible-триалов,
`bare_xray_traffic_daily` и route interactions. Порог meaningful traffic равен 1 048 576 байт.
Первое meaningful использование определяется накоплением байтов после старта триала; D1/D2/D3 —
суточным объёмом не ниже того же порога на соответствующий календарный день MSK.

Для каждого retention-дня API возвращает `eligible_users`, `retained_users` и `rate`. Текущий
незавершённый день в eligible-знаменатель не входит. Маршруты возвращают число стартовавших,
число пользователей, дошедших до meaningful traffic после маршрута, и долю; один пользователь
может открыть оба маршрута, что явно отражается отдельной метрикой `guided_after_direct_users`.

## Альтернативы

- Считать любой байт meaningful: отвергнуто, так как это сохраняет текущий шум.
- Записывать отдельное событие при каждом тике коллектора: отвергнуто из-за лишнего объёма и
  дублирования уже надёжной суточной таблицы.
- Хранить route в памяти Telegram-процесса: отвергнуто, потому что теряется при рестарте и не
  работает между polling/webhook экземплярами.

## Влияние

- **Файлы:** миграция, funnel recorder/transport, admin stats API, frontend types/UI, тесты.
- **Миграции БД:** additive nullable-by-default semantic column с idempotent constraint; данные не
  удаляются и не переписываются.
- **Безопасность:** route — закрытый enum без пользовательского текста и секретов.
- **Биллинг:** без изменений; ledger только читается существующими агрегатами.
- **Retention / lifecycle:** триал и подписка не изменяются; D1/D2/D3 — read-only аналитика.
- **VPN-провайдер:** CRUD/Reality/limitIp не затрагиваются; используются уже собранные байты.

## Открытые вопросы

- После накопления данных проверить распределение объёма и при необходимости изменить порог
  отдельной миграцией/конфигурацией, не меняя исторические определения молча.

## Критерии приёмки

- [x] Direct/guided route записывается только допустимым enum и не влияет на ответ бота.
- [x] Первый технический трафик и meaningful traffic отображаются раздельно.
- [x] D1/D2/D3 имеют зрелый знаменатель и не включают текущий незавершённый день.
- [x] `nakrut` и внутренние аккаунты не возвращаются в диагностику.
- [x] Рекламная воронка содержит meaningful traffic по кампании и итого.
- [x] Тесты покрывают порог, маршруты, зрелость D1/D2/D3 и идемпотентность миграции.
- [x] Полный pytest, frontend test/build и release health проходят.
