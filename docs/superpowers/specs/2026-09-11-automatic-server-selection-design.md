# Design Spec — Автовыбор VPN-сервера

- **Автор / ответственный:** rsidorenko
- **Дата:** 2026-09-11
- **Статус:** approved
- **Связанный plan:** `docs/superpowers/plans/2026-09-11-automatic-server-selection.md`

## Контекст и проблема

Пользователь вручную выбирает сервер из подписки, хотя фактическая доступность и задержка
выходных узлов меняются. Нужны две понятные точки подключения: обычный «Автовыбор» и
«LTE Автовыбор» для маршрутов через разрешённые CDN/входные узлы. Решение должно использовать
имеющиеся серверы и домены и не требовать покупки новой инфраструктуры.

## Цели

- Настраивать на существующем Xray entry-узле пул из двух и более действующих VLESS-outbound.
- Выбирать живой outbound с минимальной задержкой средствами Xray `observatory` + `leastPing`.
- Независимо настраивать обычный и LTE-пулы.
- При недоступности всех измеряемых outbound использовать явно заданный рабочий fallback.
- Публиковать имя автоподключения в существующей строке `vpn_servers` только после успешной
  проверки и перезапуска Xray.
- Не хранить в репозитории UUID межсерверных подключений и другие секреты.

## Non-goals

- Покупка или автоматическое создание виртуальных машин, доменов и CDN-ресурсов.
- Измерение задержки непосредственно с телефона: стандартная VLESS-подписка Happ не передаёт
  управляемую сервером клиентскую группу `urltest`.
- Выбор по максимальной пропускной способности: `leastPing` измеряет доступность и задержку,
  но не выполняет тяжёлый speed test.
- Автоматическое включение неподготовленного LTE origin из миграции `060`.

## Предлагаемое решение

Добавить операторский инструмент, который принимает локальный JSON-профиль вне репозитория.
Профиль содержит SSH-координаты существующего entry-узла, теги входов, полный набор VLESS
outbound и fallback. Секретные UUID остаются только в этом локальном файле.

Pure-функция формирует идемпотентный merge Xray-конфига:

1. добавляет/заменяет только принадлежащие профилю outbound по уникальному префиксу;
2. добавляет balancer с `strategy.type=leastPing` и `fallbackTag`;
3. включает кандидатов в общий `observatory.subjectSelector`;
4. добавляет правила `inboundTag → balancerTag`, не меняя остальные маршруты;
5. переводит перечисленные существующие foreign-outbound правила на тот же balancer,
   сохраняя российские правила `direct`;
6. повторный запуск даёт тот же конфиг.

Режим применения сначала сохраняет всех live gRPC-пользователей в `settings.clients`, затем
пишет временный конфиг, запускает `xray run -test`, создаёт резервную копию, устанавливает
конфиг и перезапускает сервис. Если тест или restart неуспешен, восстанавливается backup.

После успешной проверки опциональный `--publish` атомарно меняет label, flag и surface только
у перечисленных строк `vpn_servers`. Это исключает ситуацию, когда пользователь видит
«Автовыбор», а entry ещё работает по старому фиксированному маршруту.

## Альтернативы

- Дублировать ссылку с названием «Автовыбор»: отклонено, потому что выбор сервера отсутствует.
- Выбирать ссылку backend-пробой при обновлении подписки: отклонено, потому что выбор устаревает
  между обновлениями и не даёт failover при подключении.
- Новый отдельный gateway: технически возможен, но текущие entry-узлы уже выполняют эту роль.
- Клиентский `urltest`: лучше измеряет путь от пользователя, но недоступен в стандартной
  мобильной Happ-подписке и поэтому не покрывает LTE-требование.

## Влияние

- **Файлы:** новый операторский модуль и его тесты; spec/plan и runbook.
- **Миграции БД:** не требуются; используются существующие строки `vpn_servers`.
- **Безопасность:** межсерверные UUID и ключи передаются только через внешний JSON-файл;
  инструмент не печатает outbound-конфигурацию.
- **Биллинг:** без изменений.
- **Retention / lifecycle:** live-users сохраняются до restart; текущий reconcile остаётся
  источником желаемого состояния.
- **VPN-провайдер:** клиентские VLESS UUID, Reality и `limitIp` не меняются.

## Открытые вопросы

- Конкретные entry ID и outbound-наборы подтверждаются read-only dry-run на production перед
  применением. LTE-профиль публикуется только при наличии как минимум двух проверенных путей.

## Критерии приёмки

- [ ] Обычный и LTE-профили можно независимо собрать и применить к существующим entry-узлам.
- [ ] Каждый профиль содержит минимум два кандидата и fallback из того же пула.
- [ ] Merge не меняет чужие outbounds, balancers и routing rules.
- [ ] Повторный merge идемпотентен.
- [ ] До restart сохраняются live gRPC-пользователи; test/restart имеют автоматический откат.
- [ ] Публикация имени выполняется только после успешного применения.
- [ ] Тесты покрывают валидацию, merge, идемпотентность, откат и SQL-публикацию.
- [ ] `pytest -q` зелёный, `python scripts/run_mvp_repo_release_health_check.py` проходит.
